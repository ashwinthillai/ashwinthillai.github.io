Validating an AI-built app the way I'd validate a risk model

By Ashwin Thillai · November 2026

My job is to decide whether a model is fit to release. I've done that for 11 years, mostly with catastrophe models. Today I manage a validation team. This year I asked the same question about something new to me: could I trust an iPhone app whose code was written by an AI?

The app is Leave it to buff, a notebook for short work notes about people and projects. I designed it and I test it. Claude, Anthropic's AI model, writes the code. Here is how I check it, what held up and what didn't.

What needs checking

Most of buff runs on fixed rules, not AI. Saving a note, finding todos in plain sentences, the brief on each person's page and matching calendar events to people are all plain code. (buff's design explains why.) So most of the app can be tested like ordinary software.

Two parts use a language model and get the full validation treatment. The first is buff's helper: you type a request such as @buff what's waiting for me, and a small language model built into iOS turns it into one of buff's commands. The second is suggestions: after you save a note, the same model may suggest a name to tag or a todo it noticed. In both cases a model is making decisions about someone's notes.

Why Apple's model? I compared it with Google's Gemma 2B, an open model I could have bundled with the app. Gemma runs on more iPhones, and it can be fine-tuned. But it would add more than a gigabyte to the app, and it would need an inference engine I'd have to maintain. Apple's model is already on the phone, and the system manages it. The job is small, too: turn a short request into a command. The trade-off is that Apple's model needs an Apple Intelligence device. On other devices, buff falls back to simple phrase matching, and suggestions are off.

Deciding what "good" means, first

I wrote three pass criteria into the spec before the helper was built:

  • Accuracy. The helper picks the right command at least 90% of the time. I measure this on a golden set: a fixed list of test requests, each with the answer it should get.
  • Safety. A question never changes your notes. Read-only requests must produce zero write commands.
  • Real devices. The bar has to be met on a real phone, not only in the simulator.

Why set the bar first? Once you see results, it's tempting to move the bar to where you landed.

What the results showed

I set 25 requests aside and never used them while fixing problems. This held-out set is the closest thing to a stranger typing something new.

Overall17192% (159 of 171)

The overall score of 92% clears the bar. The held-out score of 76% does not, and it's the number I trust more. It also comes from a small sample. The 95% confidence interval (Wilson) for 19 out of 25 runs from about 57% to 89%. Even the top of that range is below 90%.

The safety result held: no question produced a change. As the helper learned new commands, the golden set grew and was re-run each time. It stayed in the low 90s: 94% of 181 requests, then 93% of 186. All of these runs were in the simulator. The run on a real device is still to do, so the third criterion is not yet met.

So the honest status is what risk teams call a conditional approval. The feature can be used. Its limits are written down. Controls are in place so mistakes are cheap.

Making mistakes cheap

The helper gets about one new request in four wrong. So a wrong answer has to be harmless. Plain code makes every decision that matters. The model doesn't.

  • Every command has a fixed label: read, write or maintenance. The model can't change the label.
  • A write never runs on its own. It appears in the input box and waits for you to press Send. Then buff offers undo.
  • If the model is unsure, buff doesn't guess. It shows up to three commands to choose from.
  • A suggestion after you save a note survives only if code confirms it: the name must already exist in your notes, or the words must be copied from the note itself. Nothing changes until you tap, and the tap can be undone.
  • AI can tidy a note's wording. Code then checks that every tag, todo and decision is still there. If anything is missing, the rewrite is thrown away. The original note never changes.
  • People you mark as private are left out of every request to any model.

The biggest accuracy gain came from the same idea. In the first run, most errors came from the model second-guessing itself. We moved those decisions into plain code. Accuracy went from about 60% into the 90s.

A finding worth the effort

After the results above, we added one new command to the model's list. The model's answers then changed in a place we hadn't touched. We re-ran the full golden set. It showed that a question about a todo would now close that todo. We caught this before release. We fixed it with a rule: a question can never produce the command that closes a todo. We didn't just reword the model's instructions.

Risk models teach the same lesson. A change in one place can move behaviour somewhere else. So the whole golden set runs again after every change.

Independent testing, even when everyone is an AI

In model risk, the people who validate a model are not the people who built it. I copied that. Each piece of work is split between separate Claude sessions with separate jobs:

  • A tester writes the tests from the written spec alone, before seeing any code.
  • An implementer writes the code and has to make those tests pass. It can propose a change to a test, with a reason, but can't make the change itself.
  • An integrator merges the work, runs everything and reports what still fails. Known failures are listed by name, not hidden.
  • For risky changes, a reviewer reads the code against the spec and the app's hard rules. I skipped this once, for the feature that edits and deletes notes, because I wanted to merge. That review is still on my list.

Each feature also has acceptance criteria written in plain language before any code, and tests are tagged to them. On GitHub, every change into the main branch runs automatically: quick checks first, then the tests for that feature. Every change that lands on main runs the full suite of about 600 tests and opens an issue if anything breaks.

Tests for promises, not just features

Some of the most useful tests check promises the app makes rather than single features. buff promises that your original notes are the source of truth. Everything else (the todo list, the index, the summaries, the widget's data) must rebuild from them byte for byte. So a test rebuilds everything twice and checks that nothing changed. buff also promises nothing is lost when you edit or delete a note. So tests check that the old text is always written to a history file first, and that two devices editing the same note end up with one note in place and the other kept as a copy.

Real devices find what tests miss

Each stage ends with a checklist on my own iPhone and iPad. Devices keep finding problems the tests missed. One build reached TestFlight with an Options button that did nothing; now a UI test taps that button. Even taking the App Store screenshots counts as a test. Driving every screen on an iPad simulator for the store pictures turned up a dark-mode screen with an unreadable title that no checklist had covered.

My rule since the first submission: no build goes to App Store review until the checklist passes on both devices. I've broken it more than once when I was in a hurry. The very first build went to Apple untested and came back with questions. Another went to TestFlight untested, and that's the one with the dead Options button. Each time, skipping the check cost more than running it would have. So the check is now step zero of the release guide, before the Submit button.

Watching a model I don't own

Apple updates its model with iOS releases. So buff's behaviour can change while buff's code stays the same. buff collects no usage data, by design. That means there is nothing to monitor in the field. The plan is simple. After each iOS update, I re-run the golden set before relying on the new model. In my day job I'm on the side that provides models. Here I depend on someone else's.

What I'd take to any AI system

  • Decide what "good" means before you look at results.
  • Keep some test data aside. Report it separately, even when it's the weaker number.
  • Keep the builder and the checker separate, even when both are AI.
  • Re-run everything after every change.
  • Put plain-code checks around the model, so its mistakes stay affordable.
  • Test the promises, not just the features.
  • Treat a vendor's model update as a model change.
